# 部署与使用文档

> 目标读者：要在**另一台电脑**上把这套工具跑起来的人。  
> 读完这一篇就能从零到「跑通第一条流程」。

---

## 0. 先回答：这个项目是什么性质？

一句话：**本体是外挂程序（旁路工具链），外面包了两层可选入口——技能包和 MCP。**

| 维度         | 结论                                                                                      |
| ---------- | --------------------------------------------------------------------------------------- |
| **形态**     | 一套独立的 Python 命令行工具（`scripts/`），通过 HTTP 接口操作已有的 Astron RPA 平台                            |
| **运行位置**   | 操作者自己的 Windows 电脑（要和设计器装在同一台）                                                           |
| **是否改服务端** | **不改**。不加插件、不改数据库、不重编镜像。服务端就是标准 Astron RPA                                              |
| **是否 MCP** | ✅ 有。`mcp/server.py` 零依赖实现 JSON-RPC 2.0 over stdio，暴露 10 个工具；`install.py` 自动登记           |
| **是否技能包**  | ✅ 有。`skill/astron-rpa-flow/SKILL.md` 是给 AI 加载的操作手册，拷进 `~/.workbuddy/skills/` 即生效        |
| **交付物**    | `flows/*.json`（流程规格）+ 平台里的「机器人 / 流程 / Python 模块」+ `docs/reviews/*.md`（评审单，**本地生成、不入库**） |



> 三者不冲突：**技能包**告诉 AI「按什么顺序做什么」，**MCP** 把「做什么」变成可调用工具，  
> **命令行**是它们共同调用的底层。装哪层取决于谁用——人用命令行，AI 用技能包或 MCP。

### 它和这三者的关系（容易混，说清楚）

```
   人    ：python scripts/ai_flow.py --spec flows/x.json     ← 命令行（本体）
   AI   ：说一句话 → 技能包 SKILL.md 指路                    ← 技能包（入口）
   其它 ：tools/call → mcp/server.py（10 个工具）             ← MCP（入口）
                              │ 三者最终都落到同一份规格
                              ▼
                    ┌─────────────────────────────┐
                    │  ai_flow.py（本项目，外挂）  │
                    └──────────┬──────────────────┘
                               │ HTTP（cookie / API Key）
                               ▼
                    ┌─────────────────────────────┐
                    │  Astron RPA 服务端（现成的） │
                    └──────────┬──────────────────┘
                               │ 本地网关 13159
                               ▼
                    ┌─────────────────────────────┐
                    │  设计器客户端（执行引擎）     │
                    └─────────────────────────────┘
```

- **技能包**：`skill/astron-rpa-flow/SKILL.md` 已实现，`install.py` 会拷进客户端读取的技能目录。  
  技能本体只有 `SKILL.md` + `PROJECT_ROOT.txt`（记录仓库绝对路径），**能力全在 `scripts/` 里**。
- **MCP**：`mcp/server.py` 已实现，零依赖（手写 JSON-RPC，不用 `mcp` 官方包，换机器不用装包）。  
  stdout 只走协议、日志一律 stderr。`install.py` 会把本机 Python 路径写进 `mcp.json`。
- **是外挂**：所有动作都走平台**已有的公开接口**（`/api/robot/*` 管理接口、`/api/rpa-openapi/*` 执行接口），相当于「用脚本代替人手点设计器」。

### 为什么必须装设计器客户端

不是因为它有界面，而是因为**两件事只有客户端能做**：

1. **登录态**：写流程要用你本人的会话 cookie（存在 `%APPDATA%\astron-rpa\.cookie.json`）。
2. **执行引擎**：真跑流程靠客户端起的本地网关（默认 `13159`）+ 内置 Python（`astronverse`）。

> 所以：**纯服务器环境跑不了本地真跑**，只能落库/发布/调用（走 openapi）。

## 1. 部署前准备

| 角色           | 需要什么                             | 说明                                     |
| ------------ | -------------------------------- | -------------------------------------- |
| **服务端**      | 一套可用的 Astron RPA（docker compose） | 已有实例直接用；对外只需网关端口（本例 `32742`）           |
| **客户端**      | Astron RPA 设计器（Windows，Electron） | 装完要**登录一次**目标服务端                       |
| **操作机**      | Python 3.10+、Git                 | Git 用来 clone；没有 Git 就下 zip 解压          |
| **AI 侧**（可选） | WorkBuddy 等支持技能/MCP 的客户端         | 只有想「说一句话让 AI 代办」才需要；纯命令行不用装            |
| **凭据**       | openapi API Key                  | 平台「开放平台 / API 密钥」页生成（只有 `invoke` 阶段需要） |

> 本项目**不需要**：MySQL 直连、SSH、MinIO、Redis。那些只在排查故障时用（`db.enabled` 默认关）。

## 2. 部署步骤

### 2.1 第一步：装设计器并连对服务端

1. 装 Astron RPA 设计器（默认 `D:\Program Files\astron-rpa`）。
2. **改服务端地址**（这是唯一决定「连哪个服务器」的地方）：

```yaml
# <安装目录>\resources\conf.yaml
remote_addr: http://192.168.76.130:32742/
skip_engine_start: false
app_auth_type: casdoor
app_edition: saas
```

1. 启动设计器，用平台账号登录一次（之后 cookie 会缓存，脚本才能读写流程）。

### 2.2 第二步：准备操作机 Python

```bash
# 建议 3.10+（本机实测 3.14 / 3.11 都可以）
python -m pip install -r requirements.txt
```

> 这一步其实可以省——下一节的 `install.py` 会自动装。只想先跑通环境就手动执行一次。  
> 注意：**流水线只需要 `requests`**。`paramiko`（SQL 兜底）、`playwright`（元素重定位）都是可选。  
> 别用 WorkBuddy 自带的 3.13 跑流水线——它没装 `requests`。**`python` 指向哪个解释器很关键**：  
> `install.py` 会把当前解释器的绝对路径写进 `mcp.json`，之后 MCP 就用它跑。  
> 先 `where python` 确认，或用完整路径（如 `C:\Python314\python.exe scripts\install.py`）。

#### ⚠️ 必做：补一个平台缺的目录（否则 DataTable 全系原子直接报错）

设计器的 `DataTable` 模块启动时会往 `%APPDATA%\astron-rpa\astron\` 下写 `data_table.xlsx`，  
但**这个目录默认不存在**，写入抛 `FileNotFoundError` 后被模块里的 `try/except: pass` 静默吞掉，  
结果所有 `DataTable.*` 原子一跑就 `NameError: PyxlWrapper is not defined`（见坑 118）。

```bash
mkdir -p "$APPDATA/astron-rpa/astron"
```

不用改平台任何代码，建完目录就正常。**换机器部署时这一步最容易漏。**

### 2.3 第三步：拿代码

```bash
git clone https://github.com/a452065754/AI-astron-rpa.git
cd AI-astron-rpa
```

> 目录名随意。`install.py` 按自身位置推仓库根并写进 `PROJECT_ROOT.txt`，所以放哪个盘都行。  
> 没有 Git 就直接下 zip 解压，效果一样。

### 2.4 第四步：一条命令装完（技能包 + MCP + 配置 + 自检）

```bash
python scripts/install.py
```

它把六件事一次做完，**每步幂等**，重复跑不会坏：

| # | 步骤         | 做什么                                                        | 跳过参数                |
| - | ---------- | ---------------------------------------------------------- | ------------------- |
| 1 | 依赖         | 装 `requirements.txt`（主链路只要 `requests`）                     | `--skip-deps`       |
| 2 | 配置         | 写 `rpa_config.json`（服务端地址 / Key / robotId）                 | —                   |
| 3 | **技能包**    | 拷 `skill/astron-rpa-flow/` 进客户端技能目录 + 写 `PROJECT_ROOT.txt` | `--no-skill`        |
| 4 | **MCP 登记** | 合并写入 `mcp.json` 的 `astron-rpa` 条目（先备份）                     | `--no-register-mcp` |
| 5 | demo 目录    | 建 `flows/` 里声明为 `*_dir` 的输出目录（否则预检直接判 error）               | —                   |
| 6 | 自检         | 跑 `doctor.py` 并打印结论                                        | `--skip-doctor`     |

**技能装到哪**（装错地方 = 装完不生效：技能不触发、MCP 工具列表里也没有）：

| 客户端                 | 技能目录                      | MCP 配置                     |
| ------------------- | ------------------------- | -------------------------- |
| WorkBuddy 桌面客户端     | `~/.workbuddy/skills/`    | `~/.workbuddy/mcp.json`    |
| CodeBuddy CLI（历史路径） | `~/.workbuddy-ai/skills/` | `~/.workbuddy-ai/mcp.json` |

脚本按「父目录是否存在」自动探测，**两处都存在就两处都写**（互不覆盖）；也可用 `--skill-dir` / `--mcp-file` 指定。

> 技能本体只有 `SKILL.md` + `PROJECT_ROOT.txt` 两个文件，它是一份**操作手册**，不含能力实现。  
> 所以技能装好但仓库被删/移动，AI 会照着手册找不到路径——`PROJECT_ROOT.txt` 是唯一的线索。

装完必须**重启客户端或新开一个会话**，技能列表里出现 `astron-rpa-flow` 才算生效。

常用参数：

| 参数                                 | 说明                                     |
| ---------------------------------- | -------------------------------------- |
| `--key` / `--host` / `--robot-id`  | 一次补齐凭据与默认机器人                           |
| `--client-python` / `--local-port` | 设计器自带 Python 路径 / 本地网关端口（默认 13159）     |
| `--print-mcp-config`               | 只打印 MCP 配置片段（给 Claude Desktop 等其它客户端用） |
| `--json`                           | 机器可读输出（凭据已脱敏）                          |

### 2.5 第五步：补凭据（**git 里没有、clone 拿不到**）

`rpa_config.json` 和 `docs/_local_secrets.md` 都在 `.gitignore` 里。两条路：

**A. 有旧机器（推荐）** — 打包带走，含清单和落地说明：

```bash
# 旧机器
python scripts/handover_export.py              # 产出 handover/，整个拷走

# 新机器：把 handover/ 放到项目根后校验
python scripts/handover_export.py --check
```

按 `handover/MANIFEST.md` 把 `rpa_config.json` 放回项目根、`docs/_local_secrets.md` 放回 `docs/`。

**B. 全新环境** — 从模板手填：

```bash
cp rpa_config.example.json rpa_config.json
```

编辑 `rpa_config.json`（**已在 `.gitignore`，不会入库**）：

```json
{
  "gateway": { "host": "192.168.76.130:32742", "scheme": "http" },
  "openapi": {
    "base": "http://192.168.76.130:32742/api/rpa-openapi",
    "api_key": "<平台生成的 Key>"
  },
  "client": { "python": "", "local_gateway_port": 13159 },
  "defaults": { "robot_id": "<你的机器人 id>" }
}
```

也可以直接让脚本写：`python scripts/install.py --key <Key> --host 192.168.76.130:32742`

配置优先级：**环境变量 > 设计器 `conf.yaml` > `rpa_config.json` > cookie 探测 > 内置默认**。

也就是说：`gateway.host` 留空也行，会自动从 `conf.yaml` 的 `remote_addr` 推出来；`client.python` 留空会自动找设计器自带 Python。

### 2.6 第六步：环境自检（**换机器后第一条命令**）

```bash
python scripts/doctor.py
```

正常输出长这样（逐项 ✅ 才算就绪）：

```
 ✅ 客户端 conf.yaml    D:\Program Files\astron-rpa\resources\conf.yaml → remote_addr=192.168.76.130:32742
 ✅ 服务端地址            192.168.76.130:32742
 ✅ 客户端 Python       ...\AppData\Roaming\astron-rpa\python_core\python.exe
 ✅ 服务端可达            192.168.76.130:32742
 ✅ 设计器 cookie 文件    ...\astron-rpa\.cookie.json
 ✅ 登录态              cookie 里有 192.168.76.130:32742 的 SESSION
 ✅ 会话有效             当前用户 xyds037
 ✅ 设计接口             design-list 正常
 ✅ 设计器本地网关          127.0.0.1:13159 在线
 ✅ 目标机器人            2115990391806255104 流程 ['主流程']
 ✅ openapi          HTTP 200，已登记 4 个可执行流程
 ✅ 依赖 requests      已安装
 ℹ️  SQL 通道           未启用（默认）

```

**每一行都带修法**（`→` 后面那句）。常见红灯：

| 现象              | 原因                                             | 修法                               |
| --------------- | ---------------------------------------------- | -------------------------------- |
| 客户端 conf.yaml ❌ | 没装设计器 / 装到非默认路径                                | 设 `RPA_CLIENT_CONF` 指向 conf.yaml |
| 登录态 ❌           | 没登录过 / 连的不是这个服务端                               | 打开设计器登录一次                        |
| 本地网关 ⚠️         | 设计器没启动                                         | 启动设计器（只是本地真跑不了，落库仍可）             |
| 目标机器人 ❌         | robot_id 不对 / 该机器人没「主流程」                       | 改 `defaults.robot_id`，或在设计器里建一个  |
| 技能包 ⚠️          | 没跑 `install.py`，或只装到了旧路径                       | `python scripts/install.py`      |
| MCP 登记 ⚠️       | `mcp.json` 里没有 `astron-rpa`，或 `server.py` 路径失效 | 同上（路径失效说明仓库被移动，重跑即可）             |

挑一条零依赖的（Excel 拆表），不需要元素、不需要额外模块：

## 4. 换到另一台电脑，到底要改什么

> 全新机器从零开始，按 §2 的六步走。这一节只列「换机后会失效的东西」。

**服务端不用动**（除非也换服务器）。操作机这边有 6 处：

| # | 要改的                 | 怎么改                                                              |
| - | ------------------- | ---------------------------------------------------------------- |
| 1 | 设计器的服务端地址           | `<安装目录>\resources\conf.yaml` 的 `remote_addr`                     |
| 2 | API Key             | `rpa_config.json` 的 `openapi.api_key`（Key 跟环境绑定，换环境要重发）          |
| 3 | 机器人 id              | `rpa_config.json` 的 `defaults.robot_id`（或干脆别填，改用 `--robot-name`） |
| 4 | **Python 子流程模块 id** | **必须重建**（模块按机器人隔离，见下）                                            |
| 5 | 规格里的绝对路径            | 一般不用手改：`nl_params.rebase_paths()` 会按文件名在项目里找回                    |
| 6 | **技能包 / MCP 登记**    | **重跑 `python scripts/install.py`**：两处配置里写的都是旧机器的绝对路径             |

### 第 4 条最容易踩坑：模块按机器人隔离

`Script.module` 节点引用的是 `module_id`，而模块**属于某个机器人**。跨机器人引用会得到 `None`，报「无法导入模块 .None」。

```bash
# 建机器人 + 上传模块 + 把新 module_id 写回规格，一条命令搞定
python scripts/make_module.py \
  --py scripts/mod_excel_split.py \
  --new-robot "Excel按条件拆表" \
  --name "Excel拆表" \
  --spec flows/Excel按条件拆表小流程.json
```

输出会打印新的 `robot_id` 和 `module_id`，规格里的 `module_id` 参数已自动更新。

### 迁移后自检顺序

```
python scripts/doctor.py                      # 1. 环境
python scripts/ai_flow.py --spec <规格> --stage draft   # 2. 结构与元素
python scripts/ai_flow.py --spec <规格> --robot-id <新id>  # 3. 真跑
```

## 6. 常见问题

**Q1：设计器里第一次点开「Python 子流程」节点，弹一次错，刷新就好了？**
正常现象，不是缺陷。客户端首次为该机器人编译 `venvs\<robot_id>\astron\main.py` 时，设计器在编译落盘前就去读取渲染。缓存后即正常。**所有用 `Script.module` 的流程都会这样**。

**Q2：报「本地网关 127.0.0.1:13159 未监听」？**
设计器没启动。启动客户端即可；如果只想落库不真跑，加 `--no-run`。

**Q3：报「找不到设计器 cookie 文件」？**
打开设计器登录一次。cookie 在 `%APPDATA%\astron-rpa\.cookie.json`。

**Q4：报「无法导入模块 .None」？**
模块按机器人隔离，跨机器人引用了别人的 `module_id`。用 `make_module.py --robot <目标id>` 重建。

**Q5：网页类流程报元素找不到？**
元素资产按机器人隔离，必须在设计器里对**这个**机器人「拾取元素」一次。
这不是「不可迁移」——**可迁移指的是这套工具**（脚本、配置、流水线换机器直接能跑）；
流程里的元素属于目标机器人的资产，换机器重新拾取一遍即可，流程规格不用改。

**Q6：说「把这个文件夹的 PDF 都转成 Word」被拦下了？**
单文件流程只处理一个文件，检测到批量意图会主动拦下（避免偷偷漏文件）。批量请用 `批量PDF版面还原小流程`。

**Q7：本机 Python 跑不起来？**
流水线只要 `requests`。若用 WorkBuddy 自带 3.13 会缺包，换系统 Python（3.10+）。

**Q8：`install.py` 说技能装好了，但 AI 还是不知道有这个能力？**
三个原因，按顺序查：①**没重启客户端**（技能在会话启动时加载，必须新开一个会话）；
②装到了旧路径 `~/.workbuddy-ai/skills/` 而客户端读的是 `~/.workbuddy/skills/`（`doctor.py` 会标出来）；
③`PROJECT_ROOT.txt` 指向的仓库被移动/删除了——技能只剩说明书，找不到脚本。
重跑 `python scripts/install.py` 一次全部修好。

**Q9：MCP 工具列表里没有 `astron-rpa`？**
看 `~/.workbuddy/mcp.json` 里 `astron-rpa` 的 `command` 指向哪个解释器。`install.py` 写的是**执行安装时的那个 Python 绝对路径**，
如果它指向一个没装 `requests` 的解释器（如 WorkBuddy 内置 3.13），工具能列出来但一调就失败。
用正确的 Python 路径重跑 `install.py` 即可覆盖。另外新登记的 MCP 服务需要客户端「信任/授权」一次才会加载。

## 6.5 服务端 AI 能力要另外配（**42 个原子的总开关**）

`OpenApi.*`（OCR/发票/身份证识别）、`ComputerUse.*`（视觉大模型操作电脑）、
`ChatAI/Agent/DocumentAI/ContractAI/RecruitAI/Enterprise` 这些域，
引擎都是**转发给服务端的 `rpa-ai-service`**：

```
本地原子 → http://127.0.0.1:13159/api/rpa-ai-service/... → .130 的 ai-service 容器 → 讯飞 / 大模型
```

**默认部署里这些凭据全是空的**，所以调用一律失败：

```bash
docker inspect rpa-opensource-ai-service --format "{{range .Config.Env}}{{println .}}{{end}}" \
  | grep -E "XFYUN|AICHAT|CUA|OCR_PROVIDER|SCNET"
# 现状（2026-11-03 实测，本项目 .130 那台）：
#   XFYUN_APP_ID=          ← 空（仅影响 5 个客户端直连讯飞的 OpenApi 原子）
#   XFYUN_API_KEY=         ← 空
#   XFYUN_API_SECRET=      ← 空
#   AICHAT_API_KEY=***     ← 已配（讯飞 maas），ChatAI 等文本域可用
#   CUA_API_KEY=           ← 空（ComputerUse 要视觉模型，仍未覆盖）
#   OCR_PROVIDER=scnet     ← 已改为超算中心 OCR
#   SCNET_API_KEY=***      ← 已配
```

典型报错（`ai-service` 容器日志）：

```
authorization_origin信息: api_key="" , algorithm="hmac-sha256" ...
ERROR - OCR service network error: Client error '401 Unauthorized' for url 'https://api.xf-yun.com/...'
INFO: 172.19.0.11:45040 - "POST /ocr/general HTTP/1.1" 503 Service Unavailable
```

客户端侧看到的只是 `BaseException: ai服务器无响应或错误`（`openapi/core_iflytek.py:167`），
**不会告诉你「是凭据没配」** —— 这是排查时最容易绕远路的一点。

**这些值只能通过部署环境变量配**，平台 UI 里没有入口
（`app/config.py` 用 pydantic `get_settings()` 读，`app/utils/ocr.py:35`、
`app/routers/computer_use.py:16`、`app/services/chat.py:10` 分别取对应 key）。

| 环境变量 | 解锁什么 | 需要什么 |
| --- | --- | --- |
| `XFYUN_APP_ID` / `XFYUN_API_KEY` / `XFYUN_API_SECRET` | `OpenApi.*` 里**客户端直连讯飞**的 5 个（营业执照/身份证/火车票/出租车票/增值税发票） | 讯飞开放平台 OCR 应用的 id + secret |
| `OCR_PROVIDER` + `SCNET_API_KEY` | `OpenApi.common_ocr`（通用 OCR 走本地网关，可改道超算中心） | 超算中心 API Key；不设 `OCR_PROVIDER` 时行为与原来一致 |
| `CUA_API_KEY` | `ComputerUse.*` 5 个 | **视觉**大模型 key（纯文本模型不行，ComputerUse 要读截图） |
| `AICHAT_API_KEY` | `ChatAI/Agent/DocumentAI/ContractAI/RecruitAI/Enterprise` 等 31 个 | 任意大模型 key；模型 id 要按该 key 实际授权填（见下） |

> **模型 id 两端不一致**：原子字典写 `maas/deepseek-v3.2`，可选值枚举却是 `xopdeepseekv32`。
> 两者对不上时用 `model="custom"` + `custom_model="<真实模型名>"`。

配好之后重启容器即可，无需改引擎：

```bash
# 改 .env / docker-compose 后
docker compose up -d --no-deps rpa-opensource-ai-service
docker logs --tail 20 rpa-opensource-ai-service
```

> ⚠️ **`docker restart` 不会重读 `.env`**。`env_file` 是容器创建时烘焙进环境变量的，
> 改完 `.env` 必须 `docker compose up -d --no-deps <svc>` 重建容器，
|  |  |
| --- | --- |
> 否则 `docker exec ... env | grep API_KEY` 还是空的（这个坑排查起来非常费时间）。

> 本项目的原子覆盖率统计里，这 42 个原子的状态是分化的（截至 2026-11-03）：
> **AICHAT 已配** → `ChatAI.single_turn_chat` 等文本类已实测跑通；
> **OCR 走超算中心** → `OpenApi.common_ocr` 已打通（`scripts/patches/apply_ai_service_ocr.py` 幂等部署）；
> **其余仍缺凭据**（`CUA_*`、讯飞 OCR 三件套、以及需要 Dify/智能体凭据的域），
> 属于**服务端没配凭据**，不是原子不能用、也不是平台缺陷。

## 7. 安全提示

- `rpa_config.json`、`docs/_local_secrets.md` 含真实凭据，**已在 `.gitignore`，不要提交**。
- 仓库文档里的凭据都是占位符（`<RPA_API_KEY>` 等），真实值以本机 `rpa_config.json` 为准。
