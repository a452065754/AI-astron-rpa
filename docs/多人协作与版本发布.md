# 多人协作与版本发布

> 建立于 2026-11-05。背景：项目从「一个人用、发现问题立刻改」转向「多人用同一套脚本 + 同一个 RPA 服务端」。
> 相关脚本：`scripts/release.py`（一键发版）、`scripts/version.py`（版本比对）、`scripts/install.py --update`（更新）、
> `logs/qa/v18_version_gate.py`（判定逻辑门禁）、`.github/workflows/`（发版与一致性 CI）。

## 1. 单人为什么不需要这套东西，多人为什么必须有

单人时版本信息只存在于「我刚改过」这个记忆里，够用。多人后有三个具体故障：

| 症状 | 真因 |
| --- | --- |
| 同事报的 bug 你复现不出来 | 你们跑的不是同一版 |
| 你说「已经修了」，他仍报同样的错 | 他没更新，或者更新失败了没人知道 |
| 生成的流程读不回来 / 字段缺失 | 两边 spec 契约不同（最危险，**当场看不出**） |

所以要做的事只有三件：**版本可读、版本可比、更新可执行**。不需要更复杂的机制。

## 2. 三条机制与对应的文件

| 机制 | 实现 | 人怎么用 |
| --- | --- | --- |
| 版本可读 | `VERSION` + `scripts/version.py --show` | 报 bug 时先贴这一行 |
| 版本可比 | `version.json`（1KB）+ `version.py --check` | 自动，启动时检查 |
| 更新可执行 | `install.py --update` | 一条命令，配置不动 |
| 变更可读 | `CHANGELOG.md`（自动生成） | 更新后自动打印最新一段 |
| **发版不出错** | `scripts/release.py` | 一条命令，推完自校验 |
| **不跑偏** | `.github/workflows/verify.yml` | 提交即查，不用记性 |

最后两行是这次加 GitHub 版本时补的。前四行解决「同事能不能更新」，后两行解决
**「我发的和别人拿的是不是同一个东西」** —— 后者才是多人协作真正难的地方，
因为它出错时**不报错**。

**版本号的唯一来源是 `VERSION` 文件**。commit 短号现取（`git rev-parse`），不落盘 —— 落盘一定会忘记更新。

## 3. 什么时候 bump 成什么

| 改动类型 | 命令 | 会发生什么 |
| --- | --- | --- |
| 修 bug、改文档、调脚本内部实现 | `--bump patch` | 同事启动时看到一行「有新版本」 |
| 新增原子支持、新脚本、新规则 | `--bump minor` | 同上 |
| **改了 spec 格式 / 必填字段 / 发布流程 / 接口路径** | `--bump minor --breaking` | 同事的 `ai_flow` **直接拒绝运行**，直到更新 |

`breaking` 不靠临场判断：commit 里带 `BREAKING:`，bump 时加 `--breaking` 即可。

```bash
python scripts/release.py --kind patch --note "修复 A15 灰度通道误用"
```

一条命令搞定，**不要手动串 `version.py --bump` + `git tag` + `--publish-json`** ——
漏掉任何一步都会让「清单」和「代码」脱节，而且不会有报错（见第 4 章）。

## 4. 发布给同事：一条命令

```bash
python scripts/release.py --kind patch
```

它把五步串成一个原子操作，任何一步失败都会停下并告诉你怎么补：

| 步骤 | 动作 | 失败会怎样 |
| --- | --- | --- |
| 1 | 校验分支 / 远端 / 工作区干净 / tag 未被占用 | 直接拒绝，**不碰任何文件** |
| 2 | 升 `VERSION` + `CHANGELOG.md`（变更从 git log 自动归类） | — |
| 3 | 重写 `version.json`（version / commit / breaking / min_supported / highlights） | 版本对不上就报错退出 |
| 4 | `git commit` + `git tag -a vX.Y.Z` | 本地已就绪，网络好了可 `--retry-push` |
| 5 | `git push` 分支 + tag | 同上 |
| 6 | **回读 GitHub Contents API，确认远端是新版本** | 明确告诉你「推了但读不到」，而不是假装成功 |

第 6 步是这套机制里最关键的设计：**`git push` 返回 0 只说明传上去了，不代表同事能读到。**

发完它会直接打印一段可复制的通知文案，贴到群里即可。

### 4.1 `version.json` 为什么在仓库根，且不走 raw 地址

2026-11-05 在本机网络实测（结论直接决定了实现）：

| 端点 | 结果 |
| --- | --- |
| `api.github.com/repos/.../contents/version.json` | ✅ **200**，实时、无 CDN 缓存 |
| `github.com/.../raw/...` | ❌ 302 之后超时 |
| `raw.githubusercontent.com` | ❌ 直连不通 |
| `cdn.jsdelivr.net` / `ghproxy.net` / `raw.gitmirror.com` | ❌ 全部 000 |

所以主源用 **Contents API**（返回 base64，本地解一次），不是 raw。它实时、无缓存，
推完立刻能读到，正好配合发版脚本的线上校验。

两个约束必须同时满足：

- `version.json` 在**仓库根**（不是 `.gitignore` 掉的 `dist/`），否则 API 照样 404
- 它必须**随发版提交**，所以 `release.py` 把它和 `VERSION`、`CHANGELOG.md` 放在同一个 commit 里

匿名额度 60 次/小时。配 24h 缓存后每人每天只查 1 次，够用；
人多了就设环境变量 `GITHUB_TOKEN`（5000 次/小时）。

### 4.2 单源 vs 多源

`rpa_config.json` 的 `update.sources` 是**有序列表，取到第一个成功的就停**：

| 配置 | 适用场景 |
| --- | --- |
| `["github"]`（默认） | **自动适配 origin**：github.com → Contents API；自建 Gitea/GitLab → 它的 raw 地址（两种路径都试）。**从哪 clone 就从哪查版本，不用改配置** |
| `["github", "\\\\fileserver\\astron\\version.json"]` | GitHub 抖动时兜底共享盘 |
| `["http://192.168.76.130:32742/version.json"]` | 纯内网、完全出不去 |
| `["file:///D:/astron/version.json"]` | 离线拷贝 |

老配置里只有 `version_url` 也认，会当成单源列表，**不用改配置**。

排障用 `python scripts/version.py --sources`，逐个打印连通性与耗时，不用猜：

```
1. ❌ github                        810ms  取不到
结论：全部不可用 —— 离线环境属正常，检查会静默放行
```

### 4.3 tag 推上去之后：Release 自动生成

`.github/workflows/release.yml` 在 tag 推送时自动做三件事：

1. 校验 `VERSION` / `version.json` / tag **三处一致**，不一致直接 fail
2. 从 `CHANGELOG.md` 抽该版本段落当正文（**只有一份变更记录**，不重复维护）
3. 建 Release；`breaking` 时正文顶部加醒目警告

这里**不上传 zip 包**：Release asset 走 `objects.githubusercontent.com`，内网机器大概率下不动。
代码更新统一走 `git pull`（`install.py --update` 做的就是这件事）。Release 页是**给人看的公告栏**，
不是分发通道。

另有 `.github/workflows/verify.yml` 管 push 到 main 时的一致性检查（见第 9 章）。

## 5. 同事侧看到的三种情况

| 情况 | 表现 | 是否阻塞 |
| --- | --- | --- |
| 已是最新 | 无输出 | — |
| 有新版本（非 breaking） | `⬆️ 项目有新版本 v1.0.1（当前 v1.0.0）` + 两条亮点 + 更新命令 | 否 |
| breaking / 低于 min_supported | `⛔ ... 当前 v1.0.0 不能继续。本轮未执行任何操作` | **是，退出码 12** |
| 离线 / 取不到 version.json | 无输出 | 否（离线是常态，不能因此拦住人干活） |

检查只读远端 1KB 文件，带 **24h 缓存**（`.cache/version_check.json`），单源超时 3s，
**所有源都取不到就静默**。所以不会拖慢每次执行。

想强制联网核对：`python scripts/version.py --check --no-cache`；临时跳过：`ai_flow.py ... --skip-update-check`。

`min_supported` 的含义：**低于它的版本一律拒绝运行**。只有真的不兼容时才往上抬，
抬了就等于强制所有人更新。`release.py --breaking` 会自动把它抬到新版本。

## 6. 更新时配置为什么不会丢

`install.py --update` 的动作是固定的，**不调用 `write_config`**：

1. `git status` 检查：有未提交改动就拒绝（或 `--force` 自动 `git stash`，可用 `git stash list` 找回）
2. 备份 `rpa_config.json` → `rpa_config.json.bak-before-update`
3. `git pull --ff-only`（有分叉就报错，**绝不自动 merge**）
4. 重铺技能包 + 重注册 MCP（幂等）
5. 重装依赖 + 跑 `doctor.py`
6. 打印 CHANGELOG 最新一段

`rpa_config.json` 在 `.gitignore` 里，本来就不会被 pull 碰到；备份是为了防 `.gitignore` 本身变更这种意外。

如果是 **zip 安装**（没有 `.git`），`--update` 会明确提示「下载新 release 包覆盖解压」，不做半吊子的事。

## 7. 多人特有的两个坑（比更新本身更麻烦）

### 7.1 共用服务端时，流程会互相覆盖

两个人同时改同一个机器人的 `process_content`，后保存的赢，**平台没有版本历史**。缓解约定：

- spec 文件名带 owner：`flows/zhang/xxx.json`
- 平台上机器人名也带 owner：`张-xxx` / `李-xxx`
- 同一流程需要两人协作时，改之前说一声，不要同时 `--stage expose`

### 7.2 「添加应用」列表只有发布者自己能看到

这不只是 A20 的坑，是所有排障的前提：`getRobotExecuteByName` 的 SQL 带 `re.creator_id = #{userId}`。
所以「我这列表挂了」别人一定复现不出来。**报障时先报三样：版本号、commit、发布者账号**。

## 8. 内网 Gitea（已部署，2026-11-09 实测）

内网已有一份完整镜像：**`http://10.18.5.61:3300/xdd/AI-astron-rpa`**（Gitea 1.22）。
它是「GitHub 访问不稳」时的实际退路，也是内网同事的克隆入口。

```bash
git clone http://10.18.5.61:3300/xdd/AI-astron-rpa.git
```

**更新提醒自动可用，不用改配置**：`version.py` 会看 `origin` 指向谁 ——
是 github.com 就走 Contents API，是自建服务就走它的 raw。已实测两个 raw 地址都能读：

| 地址 | 结果 |
| --- | --- |
| `http://10.18.5.61:3300/api/v1/repos/xdd/AI-astron-rpa/raw/version.json` | ✅ 200 |
| `http://10.18.5.61:3300/xdd/AI-astron-rpa/raw/branch/main/version.json` | ✅ 200 |

所以从 Gitea clone 的同事，第一次跑 `ai_flow` 就能拿到「有新版本」的提示。

发版时两边一起同步：`release.py` 现在会推**所有远端**，`origin` 必须成功，
其他镜像失败只警告（内网服务可能临时不通，不该因此把发版判失败）。

⚠️ **需要注意的现状**：该实例目前**允许匿名读取**，包括这个标记为 private 的仓库 ——
不带任何认证能完整 `git clone`。内网环境风险可控，但如果代码里有不该扩散的内容
（内网 IP、服务器结构、API Key），要么请管理员收紧 Gitea 的匿名访问，要么把仓库挪到有权限控制的实例。

### 其它离线环境

生产机完全出不去外网、也没有内网 git 时，按成本从低到高：

| 方案 | 做法 | 代价 |
| --- | --- | --- |
| 共享盘（**最省事**） | `version.json` 放 `\\fileserver\astron\`，配置 `sources: ["\\\\fileserver\\astron\\version.json"]` | 需要一个共享目录 |
| 内网 nginx 静态目录 | `scp version.json xudongdong@192.168.76.130:/opt/astron-nginx/html/` | 有现成 nginx 就是零成本 |
| U 盘 / 拷贝 | `file:///D:/astron/version.json` | 手工，但离线可用 |

关键点不变：**`version.json` 必须和代码在同一处、同一时刻更新**。分开发布就一定会脱节。

## 9. 排障

先跑这条，多数问题一眼定位：

```bash
python scripts/version.py --sources     # 每个源通不通、多快、读到什么版本
```

| 现象 | 原因与处理 |
| --- | --- |
| `--check` 一直返回 3 | 所有源都不通。看 `--sources` 哪一行 ❌；常见是 api.github.com 被代理拦、仓库改名、`version.json` 没提交 |
| `--sources` 里 github 取不到，但网页能打开 | 大概率是没设 `GITHUB_TOKEN` 且当天额度用完（60/h），或本地代理没给 python 走。设 token 或加共享盘源兜底 |
| 提示有新版本但 `--update` 说「已是最新」 | `version.json` 的 version 与 `VERSION` 不一致 —— 直接绕过 `release.py` 手动改过版本。跑 `verify.yml` 同款检查即可发现 |
| Release 页有了新版本，但 `--check` 说最新 | Release 是 tag 触发的，`version.json` 可能没跟着更新（有人手动打 tag）。**以 `version.json` 为准**，因为它才是客户端读的东西 |
| 发版脚本卡在第 6 步「推了但读不到」 | git 推送成功但 API 还没生效。重跑 `python scripts/release.py --retry-push` 再校验，别重新 bump |
| 推 GitHub 报 `CONNECT tunnel failed, 502` | 本地代理挡了 `github.com:443`，而直连其实是通的。`release.py` 已自动绕过代理重试；手动推就加 `-c http.proxy=` |
| 推内网 Gitea 干等两分钟超时 | 全局 `http_proxy` 把内网地址也送去代理了，代理连不到 `10.x`。`release.py` 对内网地址一律直连；手动推用 `HTTPS_PROXY= HTTP_PROXY= git push gitea main` |
| `--update` 说「有 N 个未提交改动」 | 同事自己改过文件。让他 `git stash` 或 `--force`；配置在 `.gitignore` 里，本来不该出现 |
| 更新后同事的流程报奇怪错 | 让他贴 `python scripts/version.py --show`；两边版本不同就先对齐再看 |
| 想让某人临时不更新 | 不要改他的配置；用 `--skip-update-check` 跑单次 |

### 9.1 CI 兜住的三种「静默跑偏」

`.github/workflows/verify.yml` 在 push 到 main / 发 PR 时跑，**只管一致性，不评价代码质量**：

| 检查 | 为什么必须由机器做 |
| --- | --- |
| `VERSION` == `version.json.version` | 不一致时客户端**永远查不到更新**，且没有任何报错，人眼很难发现 |
| `version.json` 六个字段齐全且类型正确 | 缺 `breaking` → 该拦的没拦住，旧脚本按新契约跑出脏数据 |
| 版本号不回退（对比上一个 tag） | 已更新的人比仓库还新，更新循环卡在「你已是最新」 |

再加两条：`v18_version_gate.py` 判定逻辑回归（不联网）、脚本可执行性冒烟。

## 10. 还没做的（真需要时再说）

- **自动更新**（不提示、直接拉）：风险大于收益。脚本在跑的时候被替换，行为不可预测。
- **强制全员同版**：把 `min_supported` 抬到当前版本即可实现，但会让离线的人彻底无法工作，慎用。
- **按人分配权限**：Gitea 侧用分支保护 + PR 就够了，不必自己写。
