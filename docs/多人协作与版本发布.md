# 多人协作与版本发布

> 建立于 2026-11-05。背景：项目从「一个人用、发现问题立刻改」转向「多人用同一套脚本 + 同一个 RPA 服务端」。
> 相关脚本：`scripts/version.py`（版本）、`scripts/install.py --update`（更新）、`logs/qa/v18_version_gate.py`（门禁）。

## 1. 单人为什么不需要这套东西，多人为什么必须有

单人时版本信息只存在于「我刚改过」这个记忆里，够用。多人后有三个具体故障：

| 症状 | 真因 |
| --- | --- |
| 同事报的 bug 你复现不出来 | 你们跑的不是同一版 |
| 你说「已经修了」，他仍报同样的错 | 他没更新，或者更新失败了没人知道 |
| 生成的流程读不回来 / 字段缺失 | 两边 spec 契约不同（最危险，**当场看不出**） |

所以要做的事只有三件：**版本可读、版本可比、更新可执行**。不需要更复杂的机制。

## 2. 三条机制与对应的文件

| 机制 | 实现 | 人怎么用 |
| --- | --- | --- |
| 版本可读 | `VERSION` + `scripts/version.py --show` | 报 bug 时先贴这一行 |
| 版本可比 | `version.json`（1KB）+ `version.py --check` | 自动，启动时检查 |
| 更新可执行 | `install.py --update` | 一条命令，配置不动 |
| 变更可读 | `CHANGELOG.md`（自动生成） | 更新后自动打印最新一段 |

**版本号的唯一来源是 `VERSION` 文件**。commit 短号现取（`git rev-parse`），不落盘 —— 落盘一定会忘记更新。

## 3. 什么时候 bump 成什么

| 改动类型 | 命令 | 会发生什么 |
| --- | --- | --- |
| 修 bug、改文档、调脚本内部实现 | `--bump patch` | 同事启动时看到一行「有新版本」 |
| 新增原子支持、新脚本、新规则 | `--bump minor` | 同上 |
| **改了 spec 格式 / 必填字段 / 发布流程 / 接口路径** | `--bump minor --breaking` | 同事的 `ai_flow` **直接拒绝运行**，直到更新 |

`breaking` 不靠临场判断：commit 里带 `BREAKING:`，bump 时加 `--breaking` 即可。

```bash
python scripts/version.py --bump patch --note "修复 A15 灰度通道误用"
git add VERSION CHANGELOG.md && git commit -m "chore(release): v1.0.1"
git tag v1.0.1 && git push origin main --tags
python scripts/version.py --publish-json      # 生成 dist/version.json
```

## 4. 发布给同事：只需同步一个 1KB 文件

`version.json` 放在**内网可达的任意静态位置**，三选一：

| 位置 | 地址写法 | 适用 |
| --- | --- | --- |
| `.130` nginx 静态目录（**推荐**） | `http://192.168.76.130:32742/version.json` | 已有服务，零成本 |
| 共享盘 | `\\fileserver\astron\version.json` 或 `file:///...` | 没有可写 web 目录时 |
| Gitea raw | `http://gitea.local/api/v1/repos/x/astron/raw/version.json` | 只用 Gitea 时 |

上传（.130 的 nginx 静态目录以实际路径为准）：

```bash
scp dist/version.json xudongdong@192.168.76.130:/opt/astron-nginx/html/version.json
```

`version.json` 内容由 `--publish-json` 生成，不要手写：

```json
{"version": "1.0.1", "commit": "a1b2c3d", "date": "2026-11-06",
 "breaking": false, "min_supported": "1.0.0",
 "highlights": ["修复 A15 灰度通道误用", "新增版本巡检"]}
```

`min_supported` 的含义：**低于它的版本一律拒绝运行**。只有真的不兼容时才往上抬，抬了就等于强制所有人更新。

## 5. 同事侧看到的三种情况

| 情况 | 表现 | 是否阻塞 |
| --- | --- | --- |
| 已是最新 | 无输出 | — |
| 有新版本（非 breaking） | `⬆️ 项目有新版本 v1.0.1（当前 v1.0.0）` + 两条亮点 + 更新命令 | 否 |
| breaking / 低于 min_supported | `⛔ ... 当前 v1.0.0 不能继续。本轮未执行任何操作` | **是，退出码 12** |
| 离线 / 取不到 version.json | 无输出 | 否（离线是常态，不能因此拦住人干活） |

检查只读远端 1KB 文件，带 **24h 缓存**（`.cache/version_check.json`），超时 1.5s，取不到静默。所以不会拖慢每次执行。

想强制联网核对：`python scripts/version.py --check --no-cache`；临时跳过：`ai_flow.py ... --skip-update-check`。

## 6. 更新时配置为什么不会丢

`install.py --update` 的动作是固定的，**不调用 `write_config`**：

1. `git status` 检查：有未提交改动就拒绝（或 `--force` 自动 `git stash`，可用 `git stash list` 找回）
2. 备份 `rpa_config.json` → `rpa_config.json.bak-before-update`
3. `git pull --ff-only`（有分叉就报错，**绝不自动 merge**）
4. 重铺技能包 + 重注册 MCP（幂等）
5. 重装依赖 + 跑 `doctor.py`
6. 打印 CHANGELOG 最新一段

`rpa_config.json` 在 `.gitignore` 里，本来就不会被 pull 碰到；备份是为了防 `.gitignore` 本身变更这种意外。

如果是 **zip 安装**（没有 `.git`），`--update` 会明确提示「下载新 release 包覆盖解压」，不做半吊子的事。

## 7. 多人特有的两个坑（比更新本身更麻烦）

### 7.1 共用服务端时，流程会互相覆盖

两个人同时改同一个机器人的 `process_content`，后保存的赢，**平台没有版本历史**。缓解约定：

- spec 文件名带 owner：`flows/zhang/xxx.json`
- 平台上机器人名也带 owner：`张-xxx` / `李-xxx`
- 同一流程需要两人协作时，改之前说一声，不要同时 `--stage expose`

### 7.2 「添加应用」列表只有发布者自己能看到

这不只是 A20 的坑，是所有排障的前提：`getRobotExecuteByName` 的 SQL 带 `re.creator_id = #{userId}`。
所以「我这列表挂了」别人一定复现不出来。**报障时先报三样：版本号、commit、发布者账号**。

## 8. 内网 Gitea 最小搭建（一次性）

1. `docker run -d --name gitea -p 3000:3000 -v /srv/gitea:/data gitea/gitea:latest`
2. 建组织 `rpa`、仓库 `astron-rpa`，把现有仓库 `git remote add gitea <地址>` 后 `git push gitea main --tags`
3. 同事侧：`git clone <gitea地址>` → `python scripts/install.py`
4. `version.json` 可以顺手放到 Gitea 仓库根，用 raw 地址当 `version_url`（省掉上传 nginx 这一步）

如果要保留 GitHub 作为主远端、Gitea 作镜像，就加一个 `git push` 的 pushBoth 别名，或者定时 `git push gitea main`。

## 9. 排障

| 现象 | 原因与处理 |
| --- | --- |
| `--update` 说「有 N 个未提交改动」 | 同事自己改过文件。让他 `git stash` 或 `--force`；如果改的是配置，注意配置在 `.gitignore` 里不该出现 |
| `version.py --check` 一直返回 3 | 地址不对或 nginx 没放文件。用浏览器直接开 `version_url` 验证 |
| 提示有新版本但 `--update` 说「已是最新」 | `version.json` 的 version 与 `VERSION` 不一致 —— 发布时漏了 `--publish-json`，或忘了 push |
| 更新后同事的流程报奇怪错 | 让他贴 `python scripts/version.py --show`；两边版本不同就先对齐再看 |
| 想让某人临时不更新 | 不要改他的配置；用 `--skip-update-check` 跑单次 |

## 10. 还没做的（真需要时再说）

- **自动更新**（不提示、直接拉）：风险大于收益。脚本在跑的时候被替换，行为不可预测。
- **强制全员同版**：把 `min_supported` 抬到当前版本即可实现，但会让离线的人彻底无法工作，慎用。
- **按人分配权限**：Gitea 侧用分支保护 + PR 就够了，不必自己写。
