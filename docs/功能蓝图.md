# 功能蓝图：AI × Astron RPA（星辰开源）

> 编号 BLUEPRINT-ASTRON-AI-001 · 更新 2026-10-30 · 维护者：接力开发团队（AI）
> 新接手的 AI：先读 `交接清单.md`，再读本文。

## 1. 愿景

让 AI 成为 RPA 的「大脑 + 双手」：
- **调度**：AI 根据用户意图，自动选择并执行已建好的 RPA 流程（填参数、触发、回收结果）。
- **搭建**：AI 根据自然语言描述，直接生成节点级流程（ProcessNode 树）写入 RPA，实现「你说流程，AI 搭流程」。
- **进化**（远期）：执行失败自动分析日志、修改流程、自愈重跑。

## 4. 路线 B 核心设计（P2）

### 4.1 生成-写入链路
1. 拉取字典：`c_atom_meta_new`（358 原子的 key + 参数 schema）→ 作为 LLM「工具规范」。
2. 拉取元素库：`c_element`（按 robot_id 过滤）→ AI 只能引用已有元素。
3. LLM 生成：节点扁平数组（格式见 §4.2），系统提示词内嵌格式规范 + 字典摘要 + 元素清单。
4. 合法性自检：key 必须在字典内；inputList 键与 schema 匹配；element 引用必须存在；id 唯一（bh 前缀）。
5. 写入：`POST /api/robot/process/save`（需会话）；新建机器人走 `/api/robot/robot-design/create`。
6. 执行：openapi `/workflows/execute-async`（API Key）。

### 4.2 节点 JSON 格式（实证，来自 c_process.process_content）
```json
[
  {
    "key": "Excel.open_excel",
    "version": "1.0.1",
    "id": "bh862228451602501",
    "alias": "打开Excel",
    "inputList": [
      {"key": "file_path", "value": "\\\\smbserver\\共享\\xxx.xlsx"},
      {"key": "default_application", "value": "Excel"},
      {"key": "visible_flag", "value": true}
    ],
    "outputList": [
      {"key": "open_excel_obj", "value": [{"type": "var", "value": "open_excel_obj_1"}]}
    ],
    "advanced": [
      {"key": "__delay_before__", "value": [{"type": "other", "value": 0}]},
      {"key": "__delay_after__", "value": [{"type": "other", "value": 0}]}
    ],
    "exception": [
      {"key": "__skip_err__", "value": "exit"},
      {"key": "__retry_time__", "value": [{"type": "other", "value": 0}]},
      {"key": "__retry_interval__", "value": [{"type": "other", "value": 0}]}
    ]
  },
  {
    "key": "Window.top",
    "inputList": [{"key": "pick", "value": [
      {"type": "element", "value": "WindowControl_xxx_1", "data": "2095084729287331840"}
    ]}]
  }
]
```

**关键规则**：
- 扁平数组，顺序 = 执行顺序；控制流（if/循环/try）用对应控制流原子包夹（`Code.*`）。
- 参数值三型：`other`=字面量 / `var`=变量 / `element`=引用元素库（`value`=元素名，`data`=element_id）。
- 标准尾部三段：`advanced`（前后延迟）、`exception`（出错策略 exit/skip + 重试次数/间隔）。
- `id` 格式 `bh+数字`，需唯一；`alias` 中文便于人读。

### 4.3 难点与对策
| 难点 | 对策 |
| --- | --- |
| 元素必须先录制 | P2 先做「引用已有元素」的流程生成；新元素提示用户在设计器录制 |
| 元素按 robot 隔离 | `c_element` 同一 element_id 按 robot_id 复制多行，跨 robot 引用运行时解析不到 → 生成时按目标 robot 过滤；目标 robot 缺 uia/cv 元素时先补录 |
| 358 原子 schema 太大 | 按分类裁剪注入（只给相关领域原子），或两段式生成（先选原子再填参） |
| robot-service 需会话 | 用 Casdoor 会话 token；PoC 阶段可从浏览器抓 token |
| 节点写入后需发布才能被 openapi 执行 | 摸清 robot_version 发布链路（P2 待办） |

- 现状：2 活（mall.jd.com 店内搜索框/按钮）、2 自动重生（商品 span、搜索 button）、8 NO_CANDIDATE（搜索框/店铺列表/进店/商品图/立即购买/提交订单，需多步导航或更强语义启发）。
- 这是 P3「执行失败→AI 修流程→重跑」自愈能力的直接前置：定位器腐烂是 RPA 流程最常见的失效率来源。

### 4.5 路线 B 流程生成器（flow_generator.py，已落地）
核心目的「自然语言 → AI 生成固定 RPA 流程」的实证实现：
- 实时从 `.130` `c_atom_meta_new` 拉真实原子 schema（落 `docs/atom_dict_cache.json` 缓存），保证生成的 `key`/参数/输出都真实存在。
- 固定流程以「模板」表达（`TEMPLATES`）：每个模板是一组原子节点 + 默认参数 + 变量连线；AI 依意图选中模板即生成确定流程（对应「固定的 RPA 流程」）。
- 输出严格按 §12.1 落库格式（扁平数组、`bh+时间戳` id、三型值、advanced/exception 尾部），并 `validate()` 校验原子存在/必填/唯一 id → IS_PASS。
- 首个模板「Excel 订单表导出」（open→read→create→save，**零网页元素**，免疫京东腐烂），已生成并通过校验（`docs/generated_flow.json`）。
- 写库 `/process/save` 与发布 `robot_version.online` 待 Casdoor 会话 token（红线，用户授权后做）。
- 已对全部 358 原子做**可用性覆盖测试**（见 `docs/atom_coverage_report.json`）：**358 全可用**——13 个双重转义坏 JSON 由生成器**读时自动修复**（DB 写入被上游 robot-service 回写、不持久），292 个无元素依赖可直接生成，66 个 UI 拾取类需真实 `c_element`。这是"建流程"之前必须完成的原子级验证（一个流程不可能覆盖全部原子）。
- 模板体系已验证可扩展：现有 3 个固定模板 —— `excel_export`（4 节点，零元素）、`text_file_copy`（`File.file_read`→`File.file_write`，2 节点，零元素）、`web_click_element`（`browser_open`→`BrowserElement.click`→`browser_close`，3 节点，含真实元素），全部 `IS_PASS: YES`。
- **元素槽位**：模板节点可声明 `"elements": {"element_data": "web"}`，生成器按目标 robot 从 `c_element` 自动取真实元素填 `{"type":"element","value":名,"data":element_id}`；目标 robot 没有该类元素时直接报错「先在设计器录制」，不生成跑不了的流程。
- **`--spec` 规格接口**：`{name, nodes:[{atom, inputs, out, elements}]}` 的 JSON 即可直接构建+校验（示例 `docs/flow_spec_example.json`）—— 这就是 LLM 的产出落点：LLM 只需吐这份 JSON，生成器负责查真实 schema、填默认值、核元素、报错定位。
- **参数默认值原则**：可选参数必须填 schema 真实 `default`（不能填空串），否则 Bool/枚举会被运行时错误强转（实测 `simulate_flag: ''` → 修成 `False`）。

#### 4.5.1 用户实测两处「看起来失败」的修正（2026-10-30）

用户在设计器里点「编辑」看到**主流程空白**、跑两条小流程**第一步就报找不到文件**。两处都不是生成器坏了，而是「生成 → 用户验收」这条链上缺了两个约束：

| 现象 | 根因 | 修正 |
| --- | --- | --- |
| 点「编辑」后主流程空白，节点在小流程里 | 建机器人时服务端自动建了一条空「主流程」，**设计器默认打开的就是它**；内容写进了新建子流程 | `publish_flow.py` 加 `--main`，内容直接写进主流程（`processId` 由 `/process/all-data` 里 `processName=主流程` 找到） |
| 两条流程第一步都「找不到文件」 | 模板默认路径是占位值（`C:\订单.xlsx`、`C:\源文件.txt`），客户端本机根本没有 | 建 `demo/` 放真实数据（`订单.xlsx` 4 行、`源文件.txt`），模板默认路径全部改指 `demo/` |

**由此确立一条原则：模板里的每个路径都必须是「生成时就能验证存在」的真实文件。** 已把这条原则写成 `validate()` 的硬校验：读取型原子（词元含 open/read/load/import，且不含 create/save/write）传绝对路径时，文件不存在直接判 `IS_PASS: NO` 并指出是哪个节点哪个参数 —— 不再把跑不了的流程交给用户。

#### 4.5.2 真机预演：schema 校验查不出的实现层陷阱

`validate()` 只能保证「原子存在、参数齐全、枚举合法」，**保证不了参数在实现层的行为**。为此新增 `scripts/verify_atoms_live.py`：用设计器自带 `%APPDATA%/astron-rpa/python_core/python.exe` 直接调原子函数（`Excel.open_excel → read_excel → create_excel → save_excel`、`File.file_read → file_write`），在真机上把「原子+参数」跑一遍。

它抓出了 3 个纯 schema 校验永远发现不了的 bug：

| 参数 | 真相 | 后果 |
| --- | --- | --- |
| `Excel.read_excel.read_range` | 是**枚举** `cell/row/column/area/all`，不是 Excel 区域串 | 填 `"A1:Z1000"` → 运行时 `NotImplementedError` |
| `Excel.create_excel.file_name` | 实现里会 `file_name += ".xlsx"` | 填 `"导出结果.xlsx"` → 产出 `导出结果.xlsx.xlsx` |
| `Excel.save_excel` 的 `file_path/file_name` | `save_type=save` 时**被忽略**（只有另存为才用） | 以为能改保存路径，实际存回原文件 |

结论：**枚举值合法性要进生成期校验（已加），实现层行为要靠真机预演（已加工具）**。两者互补，缺一个就会把「校验通过但跑不通」的流程交给用户。预演结果：excel ✅（读到 4 行、生成 8532 字节 `demo/导出结果.xlsx`）、file ✅（读出 21 字符、回读与源文件一致）。

#### 4.5.3 全流程本地执行：把「能不能跑」变成可验证的事（2026-10-30）

前面两道闸门（`validate()` 查结构、`verify_atoms_live.py` 查单原子）都证明不了**整棵节点树能跑**：变量连线、节点顺序、主流程入口、参数在真实调用链里的强转，只有真跑才知道。

**关键发现**：设计器点「运行」时，客户端会起一个**本地网关（默认 13159）**，再由 `astronverse.executor` 通过它拉 `process_content` → 编译成 Python → 执行。也就是说，**只要客户端在运行，就能不开界面把服务端流程真跑一遍**。

```bash
python scripts/run_flow_local.py --robot-id 2115990391806255104            # 跑主流程
python scripts/run_flow_local.py --robot-id X --process-id Y             # 只跑某条子流程
```

- **判据**：引擎结束时 `kill_proc_tree` 自杀，**退出码是随机的**（常见 15），唯一可信信号是日志里的 `ExecuteStatus.SUCCESS / FAIL`。工具已按此判定。
- **产物**：编译结果在 `%APPDATA%/astron/`（`main.py` / `processN.py` / `package.json`）。`main.py` 就是「节点树 → Python」的完整映射，排查生成问题直接读它最快。
- **实测**：主流程 5 节点 `SUCCESS`（4.7s），`demo/导出结果.xlsx` 被真实重写。**反向验证**同样重要 —— 故意指向不存在文件的临时流程返回 `FAIL` 并给出精确报错，证明 ✅/❌ 判据可信。
- **由此暴露并修掉的真实缺陷**：`save_excel(close_flag=True)` 只关「结果表」，**源表一直挂在 Excel 里**（残留进程 + `~$订单.xlsx` 锁文件，文件被占用到连改名都失败）。模板因此从 4 节点扩到 **5 节点**，末尾补 `Excel.close_excel(save_type_one="abort")`（abort = 不保存，只读源表绝不能反写）。

**至此「自然语言 → 生成 → 落库 → 真跑」这条链闭环**，而且每一环都有可重复的验证手段：`validate()` → `verify_atoms_live.py` → `publish_flow.py` → `run_flow_local.py`。

### 4.6 客户端 vs 服务端（2026-10-30 定论）
用户提出的关键疑问：「插件不是操作客户端吗？你是按直接操作服务端做的吗？」
- **是，按服务端做的，而且这是对的。** 设计器是 Electron 客户端（v1.1.11），`resources/conf.yaml` 指向 `.130:32742`，其前端代码保存流程就是 `POST /api/robot/process/save` —— **客户端只是 UI，没有独立数据通道**。所以「操作服务端」与「在设计器里点保存」产出完全一致的数据。
- **插件也不直连服务端**：插件 ↔ 客户端内部本地 WebSocket bridge（`astronverse.browser_bridge`），拾取后由客户端调 `/element/create` 落到服务端 `c_element`。客户端始终是中间人。
- **鉴权因此可以零交互**：客户端主进程把 `jwt` 注入请求头（仅内存），但本地 `.cookie.json` 里的 `SESSION` 对认证服务有效（`/api/rpa-auth/check-session` → true，`user/info` → `xyds037`）。落库工具复用它，不需要用户贴任何 token。
- **实测**：`scripts/publish_flow.py` 已真写进 `.130`，新建独立测试机器人「AI生成流程_测试」+ 2 条流程（主流程 4 节点 + 文本流程 2 节点），回读校验一致，已发布 v1/v2/v3；原有 8 机器人 / 92 流程未受影响。
- **边界**：`openapi_workflows`（`/workflows/get` 数据源）在服务端无写入代码，仅「发布机器人版本」不会进 openapi 可执行列表，需走应用/市场发布链路。
- **66 个拾取原子的元素校验（`--elements`，见 `docs/atom_element_report.json`）**：
  - 元素引用写法已用真实流程校准：`{"type":"element","value":"元素名","data":"element_id"}`，92 个流程 758 处引用、178 个去重 id **全部命中** `c_element.element_id`。
  - **通用档 66/66**：每个拾取原子都能用真实元素生成合法节点（证明「节点结构 + 元素引用」这一层已完备）。
  - **严格档 47/66**：只允许目标 robot 名下元素时，19 个（uia 14 + cv 5）无元素可用 —— 目标 robot `2065231113695461380` 仅有 12 个 web 元素。**缺口在元素资产，不在生成器。**

### 4.7 标准交付流程（SOP，2026-10-30 用户指定）

用户把「AI 生成流程」这件事的**验收责任划分**讲清楚了：AI 负责生成和自检，人负责运行评审，发布要人点头。

```
用户发自然语言
  → AI 生成流程
  → AI 自己校验好（结构校验 + 本地真跑，必须全绿）
  → 通知用户（附评审单）
  → 人工运行评审（设计器点「运行」）
  → 不通过：反馈 → AI 改规格 → 再验证（回到生成）
  → 通过：用户说发布/调用（或授权 AI 自行处理）
```

**一条命令承载全程**：`scripts/ai_flow.py`

| 阶段 | 命令 | 做什么 | 副作用 |
| --- | --- | --- | --- |
| `draft` | `--nl "..." --stage draft` | 生成 + 校验 | 只写 `docs/generated_flow.json` |
| `review`（默认） | `--nl "..."` | 生成 + 校验 + 写主流程 + 本地真跑 + 出评审单 | 覆盖机器人主流程 |
| `publish` | `--spec flows/x.json --stage publish --version N` | 发布版本 | 产生新版本（**须人工评审通过**） |

设计要点：

- **规格文件是唯一契约**（`flows/<流程名>.json`）。用户反馈「第 3 步参数不对」→ 改规格 → 重跑同一条命令。落库幂等，不会产生重复流程。
- **写主流程而不是子流程**：设计器点「编辑」默认打开主流程，人工评审就在那儿点运行。
- **机器自检两层**：`validate()` 查结构（原子/必填/枚举/元素归属/读取路径存在），`run_flow_local.py` 查真实执行（`ExecuteStatus`）。全绿才通知用户，避免让人白跑。
- **评审单要说人话**（`docs/reviews/*.md`）：需求原话、落库位置、逐节点参数表、机器自检结果、**本次执行新建/改动了哪些文件**、请人工确认的 4 件事、以及「不通过怎么反馈」的示例句式。
- **默认机器人是测试机器人**（`2115990391806255104`），不污染用户的真实机器人。

**实测（2026-10-30 10:47）**：「把订单表导成新文件」→ 模板 `excel_export` 5 节点 → `IS_PASS: YES`（0 错 0 警）→ 写主流程 5563 字节回读一致 → 本地真跑 `SUCCESS`（6.0s，改动 `导出结果.xlsx`）→ 评审单生成。

### 4.8 全链闭环：AI 生成 → API 调用（2026-10-30 打通）

这是整个项目的终点，也是「AI 直接操作 RPA」这句话的兑现：

```
自然语言
 → AI 生成节点树（模板/规格）
 → 校验（结构 + 元素 + 路径 + 枚举 + 参数引用）
 → 本地真跑（客户端引擎，ExecuteStatus）
 → 写主流程（设计器可见）
 → 人工评审
 → 发布版本（robot-version/publish）
 → 同步流程参数（c_param）
 → 登记 openapi 列表（rpa-openapi/workflows/upsert，带真实参数表）
 → API Key 带参调用（execute-async）→ 真实产出落地（核对内容）
 → 失败则取具体原因（robot_execute_record.execute_log）→ AI 改规格重跑
```

**关键机制（踩过才明白）**：

| 事实 | 含义 |
| --- | --- |
| openapi 执行的是**已发布版本快照**，不是设计稿 v0 | 改完流程必须重新发布，否则还在跑旧快照 |
| `COMPLETED` 不等于业务做成 | 主流程 v1 是空数组 → 4 秒「运行成功」零副作用；必须核对产出文件/内容 |
| 登记列表要用 `upsert`，不是 publish | `parameters` 是 JSON 字符串；`status=1` 才启用；**必须是真实参数表，`"[]"` 会让带参调用 403** |
| 失败信息在 `result.msg`，但太粗 | 具体原因在 `robot_execute_record.execute_log`，需解三次转义（见 §4.8.2） |

**工具落点**：`ai_flow.py --stage expose`（发布+同步参数+登记）、`--stage invoke`（API 调用+验证产出）。

**实测**：`expose` 发布 v5 → `invoke` → `COMPLETED`（version=5，4 秒）→ `demo/导出结果.xlsx` 真实重写。

### 4.8.1 参数化：让「同一个流程」能处理不同数据（2026-10-30 打通）

只有「固定路径写死」的流程是死流程。参数化之后，一个流程可以按调用方给的数据干活。

**规格写法**（`flows/*.json`）：

```json
{
  "name": "Excel订单表导出小流程",
  "template": "excel_export",
  "params": [
    {"name": "src_file", "type": "Str", "default": "demo/订单.xlsx", "describe": "源 Excel 文件路径"},
    {"name": "out_dir",  "type": "Str", "default": "demo",           "describe": "输出目录"},
    {"name": "out_name", "type": "Str", "default": "导出结果",       "describe": "输出文件名（不带扩展名）"}
  ],
  "nodes": [{"atom": "Excel.open_excel", "inputs": {"file_path": "$p:src_file"}}]
}
```

**链路**：`$p:参数名` → `{"type":"p_var","value":"参数名"}` → 引擎编译成 `参数名 = args.get("参数名", 默认值)` → openapi `params` 覆盖 → 运行时生效。

**四件事必须同时做对，缺一不可**：

| 环节 | 做法 | 漏了会怎样 |
| --- | --- | --- |
| 生成期 | 规格 `params` 声明 + 节点 `$p:` 引用 | 参数不会编译进 `args.get()`，调用方传了也没用 |
| 校验期 | `validate(..., params=)` 核对 `p_var` 引用与参数默认路径 | 拼错参数名要到运行时才炸 |
| 落库期 | `sync_params()` 同步到 `c_param` | 设计器参数面板看不到，人工评审没法改 |
| 登记期 | `upsert` 的 `parameters` 填**真实参数表** | 带参调用 403 `Arguments do not match the tool input schema` |

**实测三连**：

| 调用 | 结果 |
| --- | --- |
| 默认参数 `invoke` | `COMPLETED`，`导出结果.xlsx` 与 `订单.xlsx` **逐格一致**（A1:D4） |
| `--params '{"out_name":"参数覆盖测试"}'` | 新建 `参数覆盖测试.xlsx`，内容正确 |
| `--params '{"src_file":"客户.xlsx","out_name":"客户导出"}'` | 新建 `客户导出.xlsx`，内容 A1:D3 与 `客户.xlsx` **逐格一致** |

### 4.8.2 失败透传：让 AI 能自己修（2026-10-30 打通）

openapi 失败只回「执行错误」这种没信息量的话，AI 无法定位。真实原因在 MySQL `robot_execute_record.execute_log`，但它是 **JSON 套 JSON + 中文双重转义**：

```python
for raw in re.findall(r'"msg_str"\s*:\s*"((?:[^"\\]|\\.)*)"', log or ""):
    m = raw
    for _ in range(3):                      # 必须解三次
        try: m2 = json.loads('"' + m + '"')
        except Exception: break
        if m2 == m: break
        m = m2
```

实测：`src_file` 指向不存在的文件 → `FAILED / 5001` + `detail`「填写的文件路径有误，请输入正确的路径！」。

**为什么重要**：这是「AI 自愈」的前提 —— 没有具体原因，AI 只能瞎猜；有了它，AI 能判断是路径错、元素失效还是参数类型错，进而改规格重跑。

**还差一层**：`execute_log` 会被截断成非法 JSON（目前靠正则兜底），traceback 里的行号信息未提取。

### 4.8.3 写入原子：`edit_excel` 而不是 `write_excel`（2026-10-30 修正）

「状态成功但产出是空表」的根因是模板只读不写。修正时发现 **358 原子字典里根本没有 `Excel.write_excel`**，写入靠 `Excel.edit_excel`：

| 参数 | 值 | 说明 |
| --- | --- | --- |
| `edit_range` | `"area"` | 按区域写 |
| `start_col` / `start_row` | `"A"` / `"1"` | 起点 |
| `value` | `$sheet_data` | **必须是二维列表** |
| `edit_type` | `"overwrite"` | 覆盖 |

而 `read_excel(read_range="all")` 返回的正好是**行×列二维列表** → 读到的数据可以零转换直写结果表。

补上这个节点后，`excel_export` 从 5 → **6 节点**，产出与源表逐格一致。「空表」缺陷关闭。

### 4.8.4 三个模板全部打通 openapi 全链路（2026-10-30 11:47）

`excel_export` / `text_file_copy` / `web_click_element` 各自建独立机器人，全部走通「生成→校验→落库→同步参数→本地真跑→发布→登记 openapi→API Key 调用→**核对副作用**」：

| 模板 | 机器人 | openapi 结果 | 副作用证据 |
| --- | --- | --- | --- |
| Excel 导出 | `Excel订单表导出小流程` | `COMPLETED` | `导出结果.xlsx` 与源表逐格一致 |
| 文本转存 | `文本文件转存小流程` | `COMPLETED` | 目标文件内容=源文件；换参新建文件 |
| 网页点击 | `网页元素点击小流程` | `COMPLETED` | 测试页点击回写 `GET /clicked` |

**两个必须记住的事实**：①**发布会把机器人名改成流程名**（原「AI生成流程_测试」已被改名）；②web 元素流程依赖浏览器扩展上下文，headless 下 `127.0.0.1` 不可达、中文文件名 URL 编码不一致会报「未找到执行上下文」——演示页托管在 `.130:8899/test.html`（ASCII 名）规避。

**已知缺口（下一步）**：给目标 robot 补 uia/cv 元素（严格档 47/66 → 66/66）；LLM 直接产出规格替换关键词匹配；失败信息提取 traceback 行号。

**参数化已覆盖全部 3 个模板**：`excel_export`（`src_file/out_dir/out_name`）、`text_file_copy`（`src_file/dst_file`）、`web_click_element`（`url`）。`text_file_copy` 的编译产物实测：

```python
def main(args):
    src_file = args.get("src_file", 'F:\\...\\demo\\源文件.txt')
    dst_file = args.get("dst_file", 'F:\\...\\demo\\目标文件.txt')
```

### 4.9 PDF → Docx：能力边界与可行路线（2026-10-30 实测）

**先说结论：能转，但产出是「图片版 Word」，不是可编辑文字。**

#### 4.9.1 三条路都试过，只有一条通

| 路线 | 结果 | 原因 |
| --- | --- | --- |
| 直接转（找原子） | ❌ 不存在 | 358 个原子里没有 PDF→Word 的转换原子 |
| Word 自带 PDF Reflow | ❌ 出乱码 | `Docx.open_docx` 打开 PDF：165 段落 / 34 碎图 / 8 页（原 3 页）/ 正文 251 字全乱码。只适合有文字层的 PDF |
| OCR 后再生成 Word | ⚠️ 平台 OCR 不可用 → **已用本地引擎替代** | `OpenApi.common_ocr` 实测 **HTTP 503**，真因是 `XFYUN_*` 三个环境变量全空（讯飞 401）。改用 Windows 自带 `Windows.Media.Ocr` 后**已打通**，见 §4.9.5 |
| **页面图 → 嵌入 Word** | ✅ **可用（图片版）** | `PDF.convert_pdf_to_img` → `Docx.create_docx` → `Docx.insert_img`×N → `Docx.save_docx` |

#### 4.9.2 可行流程（8 节点，已上线 v1）

```
PDF 每页转 PNG
 → 新建 Word
 → 插图(第1页) → 分页 → 插图(第2页) → 分页 → 插图(第3页)
 → 保存并关闭
```

6 个参数：`src_pdf` / `img_dir` / `img_prefix` / `out_dir` / `out_name` / `scale`。

#### 4.9.3 两个必须知道的限制

1. **文字不可编辑**：Word 里是整页图片。要可编辑文字请走 §4.9.5 的两条路线（14:30 已打通）。
2. **旋转没有原子**：这次的原件是纯扫描件且**内容倒了 90°**（无 `/Font`、MediaBox 842×595 横向、`/Rotate=0`）。要转正只能预处理（我用 PIL 旋转后重建 PDF）。若原件方向正常，则无需此步。

#### 4.9.4 尺寸要按图片像素算

A4 纵向 + 默认页边距 → **可用宽 14.65cm**（左右各 3.17cm）、可用高 24.62cm。
`Docx.insert_img.scale` 是百分比，但换算系数随图片 DPI 变：

| 图片宽 | scale | 实际宽 | 结论 |
| --- | --- | --- | --- |
| 2287px | 24% | 14.52cm | ✅ 合适 |
| 3370px | 16% | 14.27cm | ✅ 合适 |
| 3370px | 17% | 15.16cm | ❌ 溢出 |

落地后**必须用 `wp:extent` 反算校验**，不能凭感觉设 scale。

#### 4.9.5 可编辑文字版：两条路线（2026-10-30 14:30 已打通）

判断标准只有一条：**打开 PDF，鼠标能不能选中文字。**

| | 有文本层（电子版） | 无文本层（扫描件） |
| --- | --- | --- |
| 流程 | `PDF文本层转Word小流程`（5 节点） | `PDF转可编辑Word小流程`（6 节点） |
| 关键原子 | `PDF.get_pdf_text(text_save_type="txt")` | `PDF.convert_pdf_to_img` + `Script.module` |
| 机器人 | `2116055287965179904`（v1） | `2116052553278971904`（v1） |
| 耗时 | ~5s | ~12s |
| 产出质量 | 字符 **100% 正确**，按行成段 | 正文可读可改，表格数字**个别误识** |

**路线 A（文本层直提）**：
```
PDF.get_pdf_text(text_save_type="txt") → 读 txt → 建 Word → 写正文 → 保存
```
坑：`text_save_type="word"` 能一步出 docx，但**整页文字会被塞进一个段落**（换行变空格）；选 `txt` 再走 `File.file_read` + `Docx.insert_docx` 才能按行成段。

**路线 B（扫描件 OCR）**：
```
PDF 每页转 PNG → Script.module（Windows OCR + 阅读顺序还原） → 读 txt → 建 Word → 写正文 → 保存
```
- OCR 用 **Windows 自带 `Windows.Media.Ocr`**（`zh-Hans-CN`）：离线、免费、无密钥，**不需要动平台**。
- 子流程做三件事：按 y 坐标聚行 → 行内按 x 排序还原阅读顺序 → 清洗噪声（去汉字间空格、小数点/百分号纠正、全角转半角）。
- 这是「能力降级顺序」的实证：**现有原子 → Python 子流程 → 才考虑开发新原子**。本次全部落在前两档，没有改一行平台代码。

**通用机制（值得复用的两条）**：
1. `Script.module` 是「原子不够用时」的标准出口：`c_module` 落库 → 节点 `content` 填 `module_id` → 编译成 `moduleN.py`；参数用 `module_param` + `need_parse: "json_str"`，可绑 `p_var`。
2. `c_module` **按版本隔离**：发布时必须把设计态（`robot_version=0`）的模块复制到新版本，否则 openapi 调用报「该模块不存在」（`publish()` 已内置 `clone_modules_for_version()`）。
