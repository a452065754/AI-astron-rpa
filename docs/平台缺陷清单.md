> **A17 结案记录（2026-11-03，用户目视确认）**
>
> **标准结构（从用户手工搭的 `导入MES` 流程逐字段取得）**：
>
> ```
> c_param（模块级参数定义）：module_id=<moduleId>, process_id=NULL, var_direction=0,
>                           var_type=Str, var_value='[{"type":"other","value":"默认值"}]'
>         ↓ 每行 id 就是节点里的 varId
> 节点 inputList：
>   content      = "<moduleId>"                     ← 纯字符串
>   module_param = [ {"varId":"<c_param.id>", "varName":…,
>                     "varValue":{"rpa":"special","value":[{"type":"other","value":…}]}} ]
>                                                   ← 真数组，无 need_parse
> ```
>
> **缺任一块的现象**（都实测过）：缺 `c_param` 模块级参数 → 表格「暂无数据」；`module_param` 是字符串 → 顶栏
> 「请求参数解析失败」；`content` 是数组 → 取不到模块；参数项缺 `varId` → 那一行认不到。
>
> **结论**：`baked` / `bound` 那套权衡**整套作废**（两者的共同错误是把 `module_param` 当整块 JSON 字符串）。
> 改参数的正道是**设计器节点参数表格**，不是流程参数面板。`--param-binding`、`rpa_config.json` 的
> `param_binding` 已删除；`flow_generator.build_process_content` 改为按上述结构产出，
> `publish_flow.sync_module_params()` 负责 `c_param`，`scripts/relink_modules.py` 负责把历史流程就地重建。
>
> **仍然有效的同源风险**：`varValue` 落库后引擎走 `ComplexParamParser` 求值，JSON 的
> `true/false/null` 在 Python 里未定义 → `NameError: name 'true' is not defined`。
> 所以 `spec_lint` 规则 1.5 继续把它当 **err** 硬拦（89 条 flows 存量 0 命中）。
>
> **历史证据保留**（E1 双组对照，2026-11-02）：同一流程同一模块，只改写法 —— A 组烘焙 → 写 `split`、无 `SO9999`；
> B 组 `rpa:special` + `need_parse` → 写 `split2`、`华南.xlsx` 含 `SO9999`。这条证明的是**「引擎支持运行时求值」**，
> 与落库结构无关，仍可作为引擎能力的依据；但不再是「参数可改」的唯一方案。

## 7. 结论

- **平台不是「到处都坏」**：346 个有效原子（分母已剔除 11 个作废 key）已用在流程里 **274 个（79.2%，92 条流程规格）**，**26 个域满覆盖**：Excel 35/35 · BrowserElement 22/22 · BrowserSoftware 20/20 · Docx 19/19 · Code 18/18 · ListProcess 15/15 · File 13/13 · Network 12/12 · StringProcess 10/10 · Folder 9/9 · PDF 8/8 · **Gui 8/8** · DictProcess 6/6 · Encrypt 6/6 · TimeProcess 6/6 · MathProcess 5/5 · **CV 5/5** · **Window 4/4** · **WinEle 6/6** · **Dialog 6/6** · DataConvertProcess 3/3 · Software 3/3 · DataProcess 1/1 · Report 1/1 · BrowserScript 1/1 · Script 3/3。
- **真正的硬缺陷集中在 5 类**：①覆盖旧文件不删（A3）②多输出声明与实现不一致（A5）③图片链接化（A6）④少数实现笔误（A1/A2/A4/A8/A14）⑤**通道/状态判断错误（A12/A15）**——A15（CV 灰度通道错位）和 A12（WS 未起但 `cfg["WS"]` 已设置）都是「一行代码，但让整域不可用」，比单个原子的笔误影响面大得多。
- **网页流程的拦路虎不是插件，是扩展空闲断连（A10）**——跑之前关掉浏览器，让流程自己开。
- **弹窗类原子已打通**（`Dialog` 6/6）：设计器在线时纯 API 落库 + 本地引擎可跑通；但 A12/A13 依然成立——本地**无头**执行（无设计器前端接管 WS）仍会崩/挂，必须设计器在线或点「运行」。
- **剩下的 75 个未覆盖原子，基本都是环境/凭据限制（C 类）**，不是平台坏：**AI 类 42 个卡在同一个部署缺口**（服务端 `ai-service` 的 `XFYUN_*`/`AICHAT_API_KEY`/`CUA_API_KEY` 全空 → 讯飞 401 → 网关 503；配 key 即可解锁，见部署文档 §6.5）、IE 系 36（用户已跳过）。
- **复现包当前 15/15 REPRODUCED，零 BLOCKED**，可直接发平台；平台修完后重跑 `run_all.py`，任何一条翻成 `NOT_REPRODUCED` 即视为该条已修。
